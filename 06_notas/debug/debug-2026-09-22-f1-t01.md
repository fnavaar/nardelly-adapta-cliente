# Debug Summary — F1-T01 / SPEC-1-001

- Data: 2026-09-22
- Task: F1-T01 — acesso, papéis e trilha de auditoria
- Ambiente: Skip Cloud / PocketBase v0.36, projeto 60649, versão 0.0.9

## Sintomas reproduzidos

1. As coleções base (`casos`, `pendencias`, `rotas_triagem`, `auditoria`) foram criadas inicialmente sem todos os campos e regras esperados.
2. Algumas negações retornavam HTTP 400 antes do hook de negação auditada; a trilha não recebia o registro específico.
3. A auditoria inicialmente não tinha `created`, impedindo provar data/hora e ordenar a trilha.
4. Uma rodada de login em massa acionou HTTP 429 e contaminou a evidência de alguns critérios.
5. `ativo=false` sozinho não invalidava JWTs já emitidos.

## Causas-raiz confirmadas

- No runtime Skip, o construtor da coleção base não persistiu os campos/regras usados no primeiro recorte; o padrão funcional foi `fields.add(...)`, seguido de `app.save(collection)`.
- `createRule` restritiva bloqueava a requisição antes dos hooks `onRecordCreateRequest`; os gates precisavam receber a requisição para produzir HTTP 403 e registrar a negação.
- A trilha precisava de campos autodate explícitos para registrar data/hora.
- Tokens PocketBase são stateless; revogar apenas o campo funcional `ativo` não revoga tokens existentes. A rotação server-side de `tokenKey` é necessária.

## Correções aplicadas

- Migrações 0003 e 0004: campos, regras RLS, autodates e createRules compatíveis com os gates auditados.
- Hooks de negação fail-closed: falha ao gravar auditoria bloqueia a ação.
- Hooks de auditoria ajustados para não registrar alterações que serão negadas por outro gate.
- Revogação usa `refreshTokenKey()` antes de persistir o usuário revogado.
- Provas isoladas sem login em massa, com token fresco validado antes e depois da revogação.

## Evidências finais

- QA da versão 0.0.9: setup, análise estática, build, integrações e testes passaram.
- Três negações: HTTP 403, com registros `negacao` e ator/data/estado na coleção `auditoria`.
- Autoelevação: HTTP 403, com `autoelevacao_negada` na auditoria.
- Revogação: token fresco autenticou/renovou com HTTP 200 antes; o mesmo token recebeu HTTP 401 imediatamente após a revogação; fixture restaurada.
- Preview: login da administração abriu a tela de usuários/papéis e mostrou os sete papéis funcionais.
